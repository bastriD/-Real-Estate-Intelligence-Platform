# 1. Purpose

This document records the analysis, design, implementation, validation, deployment and runtime evidence associated with **GAP-BUS-001**.

The gap concerned the ownership and lifecycle of a real-estate search request (`demande`) before and after the creation of a mandate (`mandat`).

The objective was to ensure that:

1. a client can create or own a demande **before a mandate exists**;
2. client ownership is explicitly represented in the operational model;
3. ownership is independent from version authorship;
4. a mandate can be attached later;
5. a demande can only be attached to a mandate belonging to the **same client**;
6. authorization rules respect the new ownership model;
7. historical data remains valid;
8. the behavior is enforced both by the application and PostgreSQL;
9. the implementation is tested, deployed through GitOps and verified against the running Kubernetes platform.

---

# 2. Business Context

The required business lifecycle is:

```text
Client
  |
  v
Demande
  |
  +--> Affectation d'un chasseur
  |
  +--> Versions successives des critères
  |
  v
Mandat
  |
  v
Matching / Présentations / Visites / ...
```

A demande therefore exists conceptually **before** a mandate.

The previous model had already been partially corrected by migration `005_demande_pre_mandat`, which made:

```text
demande.id_mandat
```

nullable.

However, removing the mandatory mandate relationship exposed another modeling problem.

Without a mandate, there was no reliable explicit relationship identifying the client who owned the demande.

---

# 3. Original Problem

Before GAP-BUS-001 was implemented, client ownership could potentially be inferred from:

```text
demande
   -> mandat
      -> client
```

This worked only when a mandate already existed.

For a legitimate pre-mandate demande:

```text
demande.id_mandat = NULL
```

the ownership relationship disappeared.

The model also contained author information in `demande_version`:

```text
auteur_client_id
auteur_chasseur_id
auteur_systeme
```

but these fields describe **who authored a version**, not **who owns the demande**.

Using authorship as ownership would have produced an incorrect domain model.

---

# 4. Domain Decision

The adopted model separates three concepts.

## 4.1 Ownership

The client owning the demande is stored explicitly:

```text
demande.id_client
```

This relationship remains stable throughout the demande lifecycle.

---

## 4.2 Authorship

A version may be authored by:

```text
CLIENT
CHASSEUR
SYSTEM
```

through:

```text
demande_version.auteur_client_id
demande_version.auteur_chasseur_id
demande_version.auteur_systeme
```

Authorship can change between versions.

It does **not** change ownership.

---

## 4.3 Contractual relationship

The mandate remains optional during the initial demande phase:

```text
demande.id_mandat = NULL
```

and may be attached later:

```text
demande.id_mandat = <mandat>
```

When a mandate is attached:

```text
demande.id_client = mandat.id_client
```

must always hold.

---

# 5. Resulting Domain Model

The resulting relationship is:

```text
CLIENT
  |
  | 1
  |
  | N
  v
DEMANDE
  |
  | 0..1
  v
MANDAT
```

with the invariant:

```text
IF demande.id_mandat IS NOT NULL
THEN demande.id_client = mandat.id_client
```

A client may therefore own several demandes.

A demande may exist without a mandate.

A demande may later become associated with one mandate.

---

# 6. Ownership Versus Authorship

The distinction is fundamental.

Example:

```text
Client 11 owns Demande 121
```

but version 1 may have been generated by the system:

```text
auteur_client_id   = NULL
auteur_chasseur_id = NULL
auteur_systeme     = TRUE
```

The demande still belongs to:

```text
id_client = 11
```

Later, a hunter could modify the criteria and create version 2.

That would change the version author, but the demande would still belong to client 11.

Therefore:

```text
ownership != authorship
```

# 11. Ownership Constraint

The migration introduces:

```text
ck_demande_client_owner
```

Conceptually:

```sql
CHECK (
    origine = 'GENERATED'
    OR id_client IS NOT NULL
)
```

Consequently, normal business demandes must have an explicit owner.

Generated technical/test data remains compatible with the historical dataset.

# 12. Mandate/Client Consistency Protection

A PostgreSQL validation function was introduced:

```text
real_estate.validate_demande_mandat_client()
```

Its purpose is to guarantee that a demande cannot reference a mandate belonging to another client.

---

# 13. Constraint Trigger

Migration 013 adds:

```text
trg_demande_mandat_client
```

implemented as a constraint trigger on:

```text
INSERT
UPDATE OF id_client, id_mandat
```

The trigger is:

```text
DEFERRABLE
INITIALLY IMMEDIATE
```

It protects the invariant:

```text
demande.id_client = mandat.id_client
```

whenever a mandate exists.

This creates a second protection boundary independent of the API.

---

# 14. Defense in Depth

Ownership consistency is intentionally enforced at multiple levels:

```text
API schema
    |
    v
Application service
    |
    v
Authorization layer
    |
    v
PostgreSQL FK / CHECK / constraint trigger
```

This means database integrity does not depend exclusively on FastAPI.

Even another future application or administrative process using the database remains subject to the database invariant.

# 20. Mandate/Client Application Validation

The service contains:

```text
_ensure_mandat_matches_client()
```

which retrieves:

```text
Mandat.id_client
```

and compares it with the demande owner.

If they differ:

```text
DemandeValidationError
```

is raised with:

```text
Demande client does not match mandat client
```

---

# 21. Later Mandate Attachment

A dedicated service operation was implemented:

```text
link_mandat(
    demande_id,
    mandat_id
)
```

The operation performs the following checks:

```text
Load demande
    |
    +--> demande has client owner?
    |
    +--> already linked?
    |
    +--> mandate exists?
    |
    +--> same client?
    |
    v
Attach mandate
    |
    v
Commit transaction
```

---

# 22. Idempotence

If the demande is already linked to the requested mandate:

```text
demande.id_mandat == requested mandat
```

the current demande is returned.

The operation therefore behaves idempotently for repeated identical attachment requests.

---

# 23. Relinking Protection

If a demande is already linked to another mandate, attempting to replace it through this operation is rejected.

This avoids silently changing an established contractual relationship.

---

# 24. Ownerless Demande Protection

The service explicitly prevents an ownerless demande from being linked to a mandate:

```text
Demande has no client owner and cannot be linked to a mandat
```

This is particularly important for the historical `GENERATED` records whose ownership was intentionally not fabricated.

A CLIENT identity may access only demandes belonging to its:

# 31. Client Creation Rules

When a CLIENT creates a demande:

```text
payload.id_client
```

must correspond to the authenticated client's identity.

Client authorship is also bound to the authenticated identity when the client is the author.

A client therefore cannot create a demande on behalf of another arbitrary client.

---

# 32. Client Revision Rules

A client may revise its own demande.

The authorization layer validates ownership before the revision is created.

Version authorship remains separate from demande ownership.

---

# 33. Restricted Lifecycle Operations

The mandate attachment endpoint is restricted to:

```text
ADMIN
CHASSEUR
SERVICE
```

A CLIENT cannot arbitrarily attach a mandate.

Similarly, arbitrary status transitions remain restricted according to the existing business authorization rules.

---

# 34. Authorization Helper

The authorization layer now uses demande-aware access enforcement conceptually represented by:

```text
enforce_demande_access()
```

It evaluates:

```text
ADMIN/SERVICE
    -> allowed according to service policy

CLIENT
    -> demande.id_client must match identity.id_client

CHASSEUR
    -> valid demande assignment required
```

This keeps authorization aligned with the domain model.



# 69. Data Integrity Impact

Migration 013 improves relational integrity by introducing an explicit domain relationship rather than relying on inference.

Important integrity rules now include:

```text
demande.id_client -> client.id_client

IF demande.id_mandat IS NOT NULL:
    demande.id_client = mandat.id_client
```

This is especially important because the demande and mandate lifecycles no longer begin simultaneously.

# 71. Known Boundary — Mandate Lifecycle Status

The current `link_mandat()` implementation verifies:

* demande owner exists;
* demande is not already linked elsewhere;
* mandate exists;
* mandate belongs to the same client.

It does **not currently validate mandate status** before attachment.

For example, ownership consistency alone would not prevent attachment to a `TERMINE` mandate.

This was deliberately avoided in the controlled E2E test by selecting active mandate 11.

This observation is **not a failure of GAP-BUS-001**, whose scope is client ownership and ownership consistency.

However, mandate eligibility at attachment time should be treated as a separate business-rule review if the specification requires only active/current mandates to be attachable.
